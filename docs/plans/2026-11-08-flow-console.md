# Flywheel 流程控制台交互设计与实施方案

2026-11-08。状态为已确认设计、完整控制台源码与故障验证进行中。基线为 Flywheel 0.29.1、`1087b686fa308284b6b68f238129f6779e0ba113`。用户本轮选择先审阅交互设计与实施方案。界面示例使用虚构任务，交互只修改原型草稿。

## 1. 产品结构

保留 DSH 原生「Flywheel」会话视图，位于「统计」之后。内部提供「运行画布」「配置」「运行对比」三个页面。通过 DSH 公开全局面板入口提供项目和配置入口，全局面板注册方式在实施前用当前桌面版本验证。

顶部始终显示仓库链接、项目路径、当前分支、任务集成分支、worktree、DSH 来源会话、task ID、run ID、配置版本、数据更新时间。路径较长时折叠显示，并可复制完整值。

- 全局入口先展示全局设置、已明确登记的项目和最近运行。
- 会话入口根据确切的 launch/start 回执选择对应任务。一个会话关联多个任务时保留列表，并标记当前选择。
- 终端运行进入已登记项目的运行列表，用户可主动将该运行关联到当前 DSH 会话。
- 未关联任务时显示「准备新任务」「打开已有任务」「查看全局配置」。准备任务的交互复用 `/flywheel-task` 或 `/flywheel-new`。

身份分为四层。项目承载仓库和配置，任务承载 spec/packets，运行承载配置快照和一次执行，Provider session 承载某一角色的模型历史。DSH 来源会话单独显示，避免与 Provider session 混用。

## 2. 画布与阶段

画布采用从左到右的阶段图。调度节点向上下分出任务，各任务的执行、测试、Review 和提交步骤在当前画布中向右展开。展开时保留主流程与其他任务，后续聚合和交付节点自动右移；再次点击可收起。前置任务的结果通过依赖边汇合。节点使用稳定 ID，刷新更新状态时保留位置、平移和选中项。

画布支持空白处拖动、触控板横移、左右移动按钮，以及按阶段定位和定位当前节点。节点保持可读尺寸，长流程在画布内部横向浏览，窄屏仍保留左右流向。节点详情位于画布下方，避免压缩流程的横向空间。

Full 的总览结构如下。

```mermaid
flowchart LR
  A[需求与获准范围] --> B[Plan 与任务拆分]
  B --> C[调度与依赖]
  C --> D[任务分支]
  D --> E[集成与聚合]
  E --> F[L2 / L3 与 Judge 终验]
  F --> G[远端 PR 与检查]
  G --> H[远端 Merge]
  H --> I[发布 · 可选交付目标]
```

每个任务分支展开为「资格／依赖 → Execute → L1／适用缺陷抽检 → Review → 单元提交与集成」。Review 退回的边返回该任务的 Execute，并标记第几次返修。Review 复审读取自己的历史。verification-gap 的边返回 Plan 修订契约。聚合视图展示各单元进入集成候选的结果及冲突。

| 用户看到的阶段 | 0.29.1 的实际归属 | 模型配置位置 |
|---|---|---|
| 需求准备、初始拆分 | 宿主 skill 研究并生成契约 | 显示来源 DSH 会话模型 |
| Plan 与契约修订 | Go 的 Plan Loop | `loops.plan` |
| 调度 | Go 依赖与资格判断，当前顺序执行 | 确定性阶段 |
| 执行 | packet 选择 route | `routes.default/frontend/hard` 或显式自定义 route |
| 测试 | L1/L2/L3 及缺陷抽检 | 展示命令、结果、候选和退出事实 |
| Review | 每个 packet 的独立评审 | `loops.review` |
| 集成与聚合 | 单元 Git 提交、worktree 集成、里程碑 gate | 确定性阶段 |
| 最终裁决 | Full 的 Judge 和可选第二意见 | `loops.judge`、`judge-panel` |
| PR / Merge | 待接入的远端交付追踪 | 仓库授权与远端状态 |
| 发布 | 可选目标，绑定版本、候选和环境 | 发布流水线与实际产物回执 |

原型会把 Plan 和拆分画成相邻节点，以展示产物流向。真实状态由宿主准备回执、Plan 调用及契约验证投影得到。缺少独立阶段证据时展示「阶段内活动」或「待取证」，避免根据后续成功推断前面每一步的时间。

### Full、ultraWork 与 Auto

`ultraWork` 是本方案建议采用的 Quick 产品名称，后端继续使用 `quick`。Auto 保持 Go 按契约资格选择 Quick 或 Full。选择器同时展示请求模式、生效模式和判定理由。

ultraWork 的画布为「准备并冻结契约 → 单任务 Execute → 必需验证 → 独立最终 Review → Git 交付 → 可选远端 PR/Merge」。Plan/Judge 显示「本流程不适用」及理由。Quick 升级 Full 时保留原运行、预算、尝试和证据，画布展开新阶段。已运行的 Full 保持其持久化策略，切换入口提供创建新运行草稿。

## 3. 状态与细节

### DSH 视觉规范对齐

2026-11-08 复核 DSH 当前 UI 规范、对齐与间距说明，并参考宿主 Button、SegmentedTabs 和主题别名。控制台沿用宿主字体，信息正文采用 13px/20px，辅助信息采用 12px/18px，页面标题采用 18px/28px，区块标题采用 14px/22px。feature 字重最高 500。

普通操作使用 H36/R12，紧凑工具使用 H28/R8，输入与选择器使用 R12，独立任务节点和配置卡使用 R20。选中、悬停、焦点和禁用状态保持相同尺寸。主按钮采用宿主主色的深浅对比，次操作用中性描边或 ghost。运行状态用小面积色点和文字表示，选中节点使用业务色细线与浅底。

降低重复边框和表单噪声，将阶段定位改为轻量导航。节点中的 Provider / 模型保留可读字号，统一行距与左边线。节点详情顶部集中放置运行、重跑和接管操作，下方以紧凑页签切换证据与会话。图上的端口按固定节点尺寸居中连接，展开后保留可见返修回边。

生产实现消费 `--dsw-alias-*` 和宿主圆角变量。设计稿以同角色的亮暗色值预览这些效果。圆角支持时沿用 `superellipse(1.5)`，状态圆点保持圆形。触屏操作区域至少 44px，窄屏表单与详情纵向排列，横向画布保持独立平移空间。

颜色始终配文字和图标。远端 PR 状态与引擎任务状态分别展示。引擎完成后，远端检查失败仍会保持在交付阶段。终止、取消、失败与完成各自独立。

画布下方的节点详情面板提供「概况」「配置」「证据」「Session」「历史」页签。窄屏将详情字段纵向排列。任务详情列出需求、依赖、route、worktree、branch、candidate SHA、尝试数、L1/L2/L3、Review findings、返修记录、错误码、日志片段及 PR 链接。只显示当前候选有效证据，旧证据进入历史。

刷新策略建议为可见且运行中的画布每 2 秒进行一次有界只读查询。停止运行后每 10 秒刷新，隐藏时暂停。一次只保留一个查询，指数退避最多 30 秒，并显示最后更新时间。宿主会话切换后丢弃旧身份的迟到响应。轮询是本次拟议增强，需更新现有设计中「不周期轮询」的描述和对应测试。

## 4. 配置先行

配置页面提供「全局配置」「项目配置」「本次运行快照」。前两项可编辑，运行快照只读。每次保存均显示目标文件、SHA-256、完整差异和生效时机。

当前优先级是任务目录配置 → 项目配置 → 全局配置 → 内嵌模板，选择一份完整文件。项目首次配置从当前有效配置生成完整草稿。UI 显示实际选中的文件；项目文件存在时，提示全局编辑对该项目的覆盖关系。未来若引入逐字段继承，需另行修改配置契约。

「使用本版本默认配置」导入完整内嵌模板并给出差异。「保存项目配置」写入明确项目根下的 `flywheel.config.json`。「应用到全局」写入当前全局配置路径。两个保存按钮分别说明影响范围，原型只预览保存结果。

每个模型 loop 配置资源渠道、Harness、模型、推理等级、会话策略和权限。用一个可读的渠道选择器生成一致的 harness/provider/channel 组合，高级区保留真实字段和 Provider 名称。模型候选以本机后端能力为准，同时允许填写明确模型 ID 并校验。

| 资源入口 | Harness / Provider | 模型初始值 | 默认阶段 |
|---|---|---|---|
| ChatGPT · DSH | `dsh` / `chatgpt` | `gpt-6.1-sol`、`gpt-6-astra` | Review、Judge |
| ChatGPT · Codex Pro | `codex-pro` / 原生订阅 | `gpt-6.1-sol` | hard Execute |
| Kimi Code | `kimi` / 原生订阅 | `kimi-code/k3.1-pro` | Plan、frontend、Garden |
| DeepSeek Account | `dsh` / `deepseek-account` | `deepseek-flash` | default Execute、Intake |
| Claude Code Pro | `claude-code-pro` / 选定账号渠道 | 先用 CLI 别名 `sonnet`，也可选明确模型 | 用户指定的 loop／route |

当前 Claude 适配器精确要求 0.4.0，桌面单独安装的 0.3.1 应显示「需要匹配适配器」，并引导正常安装流程。协议导入成功、账号已授权、模型实际可调用分别提供证据状态。

全局区还包含预算、重试上限、超时、worktree、测试命令入口、默认流程、会话质量重建阈值和调度草稿。测试命令归任务契约维护，配置页面链接到对应契约编辑与校验流程。

0.29.1 权限仅支持顶层 `permissions.mode`，取值为 `role-based` 或 `full-access`。按 loop 的权限覆盖需要新增 schema、解析和所有驱动的接纳验证。首版先展示每个阶段的有效权限及全局选择，逐阶段权限编辑在后续接口就绪时启用。账号密钥输入继续交给 Provider 的正常登录入口。

保存流程为读取完整草稿 → schema/语义校验 → 展示差异与目标 → 用原内容摘要进行并发检查 → 同文件系统原子写入 → 重读实际配置。项目内的符号链接、路径别名、并发编辑和写入失败必须有明确结果。新增通用配置写接口复用现有迁移代码的路径和原子写入机制。

运行期间保存草稿，界面标记「下次新运行生效」。涉及当前任务时，先等待或停止已有调用并核对 pending 回执，再允许激活新配置。未消费结果的旧绑定继续用于恢复验证。运行快照始终展示本次实际使用的配置摘要。

## 5. Session 策略与跳转

用以下四项取代单个「会话恢复」布尔字段。

- 历史策略显示「同任务同角色续接 scoped」或「每次新会话 fresh」。
- 隔离范围显示 task、packet／milestone、role。独立任务和不同角色始终隔离。
- 本次动作显示新建、续接、重建或核对回执，附原因、generation、invocation ID。
- 运行事实显示派发、终态、清理、历史可用性及只读 recovery 能力。

Intake/Garden 标记为当前通用角色续接策略之外。支持续接与本次实际续接成功分别显示。每次 worker 进程重启时，Provider session 仍可在资格匹配后沿用。

点击「查看会话」优先使用 Provider 已验证的只读历史入口。DSH SDK 会话通过公开导航 API 和准确 session ID 打开，若当前桌面 profile 无法读取对应历史则显示原因和日志入口。实现前核对 DSH 的实际公开导航及存储兼容能力，避免拼接猜测的 URL。

终端入口显示 cwd、后端 home/profile、session ID、可执行程序版本和一条可复制的命令。本机帮助已确认以下原生形态，具体权限、home/profile、session 所在目录仍须由适配器验证。

```sh
cd -- '/absolute/worktree' && codex resume 'exact-thread-id'
cd -- '/absolute/worktree' && kimi --session 'exact-session-id'
cd -- '/absolute/worktree' && claude --resume 'exact-session-id'
```

最终按钮建议生成带任务租约检查的 Flywheel 包装命令，再通过 argv 启动原生 CLI。它是待新增接口。进入前检查当前 writer、后端恢复能力、持久化句柄和清理事实。运行中提供「查看历史」，需要交互写入时走「暂停并接管」。人工接管期间锁住引擎继续，归还时重新检查工作区、验收与权限。未知派发／结果时保持阻断。复制按钮仅负责复制，运行命令前还须重新检查租约以处理时间差。

## 6. 串行与并行

### 节点级交互执行

节点详情的主操作随状态变化。鼠标选择、键盘选择和任务列表入口调用同一个受管操作。

| 节点情况 | 主要操作 | Go 接纳条件与结果 |
|---|---|---|
| 待开始且前置已满足 | 运行此节点 | 获得任务租约，核对候选与配置，只执行获准的该阶段 |
| 待开始但前置未满足 | 查看前置条件／运行所需前置 | 返回阻塞节点；明确选择后由引擎推进前置，不把未完成节点置为通过 |
| 失败且调用已结束、清理已确认 | 重跑此节点 | 新 attempt，按有效策略续接对应角色历史，沿用预算和累计失败次数 |
| 自动重试耗尽 | 人工继续一次 | 展示失败摘要与继续理由，记录一次有界人工授权；额度/权限不足时仍需先处理 |
| 正在运行 | 查看输出／请求停止 | 确认进程收尾后才转入可重跑或接管状态 |
| 结果未确认 | 核对上次结果 | 查原调用证据，完成核对后再提供安全的继续动作 |
| 已完成 | 重新执行 | 显示将失效的下游测试/Review/交付证据，接受新候选后重新验收 |
| 人工接管中 | 验证修改并交回流程 | 重读候选和契约，失效旧证据，进入必需验证与独立 Review |

可接纳的待开始／普通失败节点支持一次点击发出操作，按钮显示待确认状态。成功响应后刷新节点。双击、刷新、重连、重复请求通过 operation ID 和任务身份去重。超时不自动再次派发。

运行某节点与继续整个流程是两个按钮。单节点运行结束后显示「阶段已完成，流程等待继续」，由用户选择继续。执行器内部仍可完成其有界 Execute/L1 循环，界面提前显示这一操作包含的范围。

现有 `run --only` 和 control start/stop 可复用其引擎逻辑。需要新增版本化节点命令，将 node ID、expected revision、candidate SHA、operation ID、单节点／流程范围和人工继续原因提交给 Go。所有作用域判断、前置门禁、证据失效和 attempt 更新由引擎完成。

「进入会话自己发 prompt」使用前节的受管接管流程。用户可以在 Provider 桌面或 CLI 内修改成果，交回时 Go 重新验证。接管记录包含角色、原 session、worktree、起始候选、归还候选和授权范围；人工修改不能直接形成 Review pass。

发布、push、PR 和 Merge 节点的重跑先核对原目标及外部结果。例如 npm 包已经存在时核对原 tarball integrity，PR 已合并时读取实际 merge commit。已确认完成的外部操作显示其回执，部分完成的操作从缺失步骤继续。每个发布节点绑定版本、源码、候选与目标环境，并使用该交付范围的已有授权。

默认串行沿用现有引擎。并行模式的拟议配置包括最大并发、依赖、文件范围冲突、Provider 配额、预算和集成队列。独立就绪任务可并行，依赖未满足的任务保留等待原因。相互冲突的写入任务进入串行队列，每个并行执行单元使用独立 worktree。

调度仍由单一 Go 状态写入者统一接纳结果并 CAS 保存。重启必须找回所有在飞调用，停止必须覆盖所有子进程组。集成和最终候选验收串行执行，避免两个完成结果覆盖彼此。界面通过 capabilities 展示并行可用性，0.29.1 上只能预览并行方案。

拖动节点仅改变画布位置。改依赖、重排执行顺序、换模型属于运行方案编辑，需校验与明确激活。运行中的模式切换安排在所有受影响调用达到可信终态之后。

## 7. 自动关联与 CLI 发现

已存在的 `flywheelTask` projection 消费本会话 command/tool/PTC 的确切参数和回执。保留其 fork 隔离和结果未确认保护，扩展为多个任务的关联列表。

skill 被提及只显示「准备中」。真正的任务定位来自准备回执里的物理 taskDir/cwd，以及之后的 launch 回执。计划新增 preparation 类型回执，让 `/flywheel-new` 准备出的任务也能打开画布。

CLI 入口增加受管运行索引，记录 repoRoot、taskDir、cwd、branch、run ID 和最近控制操作 ID。索引提供候选列表，活跃状态仍向 Go 查询。索引按用户私有目录保存，通过原子更新协调并发登记，并处理失效目录。发现范围限于已登记项目，避免搜索整个磁盘的 `state.json`。

项目、任务、运行、Provider session 使用稳定身份。分支只作为标签与归属信息，同分支可有多个任务，同一任务也可有多个 worktree。显式关联用于把终端运行接到 DSH 会话；模型文本里的路径和裸 skill 名称不自动建立运行关系。

## 8. 成本、延迟与质量

运行对比按任务／契约版本、工作流、模型、thinking、权限和 session 策略分组。显示样本数、成功／失败／未完成数、首次验收率、返修次数、回归与遗漏、端到端时延及各调用时延。

用量保留 complete/partial/unknown，成本展示已知金额和缺失调用数。订阅调用缺少价格时显示「费用未报告」。P4 配对报告可导入并链接独立 oracle。只有条件相同的配对任务支持收益对比，原型使用「待采集」占位。引擎账本中的迟到 correction 按同一 invocation 对账后统计。

## 9. 数据和接口拆分

UI 通过 Go 的 JSON 接口读取状态和操作任务。新增只读投影统一计算节点、边、状态和能力，避免 React 根据多个字段自行重建状态机。沿用当前接口兼容旧客户端，新投影带独立 schema 版本。

| 数据 | 当前来源 | 拟议补充 |
|---|---|---|
| 运行和任务 | `control status` 的 state/packets/milestones | run ID、阶段 projection、稳定节点 ID、current candidate |
| 工作区 | packet.worktree/base-ref/commit | repo 身份、integration branch、当前 HEAD |
| 模型和策略 | `control config` 的 bindings/session | 文件摘要、编辑 schema、能力目录、运行配置快照 |
| session | state.sessions 与紧凑 sessions 投影 | 受控目标信息、查看／接管能力、租约 |
| 失败和测试 | evidence/history/last-feedback/retry-history | 有界报告索引、候选有效性和原始证据链接 |
| 成本与延迟 | metrics、budget、P4 reports | 有界分页、去重聚合和对比条件 |
| PR | 当前由宿主／用户完成远端交付 | repo + PR number + head SHA + checks/review/merge 状态与更新时间 |

PR 关联以当前运行的提交和分支为依据，远端 HEAD 变化时失效旧检查。首版提供打开仓库／PR 和只读刷新，后续开 PR、push、merge 操作遵循用户已有授权和仓库规则。引擎的本地 worktree merge 与 GitHub PR merge 分开呈现。

建议修改点为 `plugins/dsh/src/client.js`、`client.module.css`、新增 canvas/config/session 组件、`task-association.js`、`index.js`、`control.js`，以及 `internal/cli` 的只读 projection、`internal/config` 的受管保存、`internal/diagnostic` 的能力解析。并行、session 接管和远端写操作分别作为后续引擎变更。实际协议改动同步 `PROTOCOL.md`、schema、中文与英文用户指南。

## 11. 原型审阅重点

交互原型提供总画布与任务子画布、配置作用域和映射编辑、Full/ultraWork、串行／并行草稿、返修／未确认示例、Provider 会话详情以及待采集的对比页面。配置保存反馈明确表示本地设计草稿。

建议先确认画布层级与节点详情是否符合日常操作，再确认全局／项目配置的作用域，最后确定并行调度和接管入口的优先级。首版实施以 A、B 为一组，C–E 按接口依赖继续交付。

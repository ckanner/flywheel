# P5：就绪队列与有界运行时预热

[方案索引](README.md) · [原整体方案](2026-11-12-feedback-driven-workflows.md) · [系统设计](../design.md) · [当前配置](../zh-CN/configuration.md#就绪队列与运行时准备) · [工程验证](../validation/2026-11-13-p5-ready-queue-prewarm.md)

## 1. 本轮决定与交付边界

原整体方案将 P5 调度与运行时优化放在瓶颈测量之后。PR #37 的
`c445393c4f7238677146028b89efe520253f8318` 已完成 JEV 执行决策扩展，
其工程验证记录明确保留了 P5。用户随后要求把这些工程能力也补齐，真实账号、
性能及 Mac 桌面验收留到后面。本记录描述这次新增实现决定，保留前次记录的历史事实。

本轮缩短两类可控等待：独立 packet 的批次尾部等待，以及下一次 Review 的 SDK
初始化等待。优化受确定性调度、实际回执、冻结契约、预算和相同候选验收约束；
不以更短的离线 fixture 时间宣称真实模型更快，也不改变模型／账号默认。

| 范围 | 本轮决定 | 保持的边界 |
| --- | --- | --- |
| Ready queue | 在有界 Execute／L1 窗口中按空位接纳已就绪独立 packet | 冻结依赖、写入范围、独立 worktree、实际渠道并发与共享预算 |
| 流水化 | 独立执行槽位及时补位；串行 packet 的确定性检查与下一 Review runtime 初始化重叠 | Review 推理、Plan 修订、Git 集成仍在安全屏障后执行 |
| 预热 | 通过 DSH SDK 公开初始化能力准备一个待用 Review runtime | 无模型 prompt，精确绑定与权限，未使用也须有界清理 |
| 已有候选 | 评估现有受管 Session 交回与任意补丁接纳的差异 | 通用补丁导入独立排期，不伪造 Execute 来源 |
| 默认策略 | 新设置缺省 `batch`／不预热 | 真实收益验收后再决定是否更改安装默认；不改用户配置 |

工程验证结果单独进入验收记录。合并、npm 发行、用户安装和实际账号验收不由本计划
代替；计划中的验证矩阵也不等同已经执行的测试。

## 2. 配置与产品职责

新增两个可选 scheduler 字段：

```json
{
  "scheduler": {
    "mode": "parallel",
    "max-parallel": 2,
    "providers": {"deepseek-account": 1},
    "dispatch": "ready-queue",
    "prewarm": true
  },
  "worktree": {"enabled": true}
}
```

这是显式启用的示例。安装模板与字段省略时都保留 `dispatch:"batch"`、
`prewarm:false`。已有完整配置省略 scheduler 时仍为 serial；新安装模板的
parallel／最大 2 保持。`providers` 键仍是实际 channel 名称，不改成 provider ID。

| 选择层 | 职责 |
| --- | --- |
| Task／New／Run 和单阶段入口 | 目标准备、方案审阅、运行／恢复与明确干预 |
| Auto／Quick／Full | 按资格选择实施流程与必要阶段 |
| scheduler | 在既有流程与权限内安排可以重叠的工作 |
| `jev.enabled` | 唯一的 JEV 调查与执行决策总开关 |

不增加新的工作流模式或 JEV 子开关。配置编辑器支持新增字段，保存遵守原文件
revision、备份与原子发布规则，当前进程继续使用已载入快照。下次启动可以选择新的
调度策略，但原 invocation、未知结果和未完成共享批次仍按原记录核对。`state.scheduler`
记录本次实际载入策略，不被描述成不可变化的首次策略冻结。

## 3. Ready queue 的接纳与停止

适用条件同时为 Full、`scheduler.mode=parallel`、`dispatch=ready-queue`、
最大并发大于 1、自动管理 Worktree 开启。Quick、serial、最大并发为 1 保持原路径；
自动管理关闭时一概使用既有 batch，包括之后可能登记外部 worktree 的情况。

1. 从当前已冻结契约中收集全部已就绪、互相独立的候选，保留稳定的 packet 顺序。
   依赖须已经交付，写入范围须明确且互不重叠；没有声明或需要 live 凭证的任务保持
   原串行规则。固定本轮候选集，运行中的模型不能添加任意队列项。
2. 先为首个有界窗口全部准备独立目录并持久化，成功后才派发。总并发和渠道限制
   仍在实际模型派发前重核，hard 预算仍限制未结算的在飞模型调用。
3. 一个 worker 完成 Execute／L1 后，协调器可为下一项准备目录并 CAS 保存，再
   占用空位。未接纳项不提前创建目录、不改 packet 状态、不写 invocation 意图。
4. 补位准备失败、未知效果或取消停止新接纳，取消并等待已启动工作；不会退回
   共享目录继续并发。尝试耗尽或空转也停止补位，停稳后仅处理实际已启动集合。
5. 所有已启动 worker 收尾后，进入原有串行 Review、升级／Plan 和集成。Plan 改变
   契约后重新选择候选，不能继续使用旧队列。后续分支吸收已交付成果，再在合成候选
   上复验。分支自身绿灯不能代替共同候选证据。

协调器继续拥有权威状态，worker 仅持有私有视图。packet、session、用量、JEV
请求和效果沿原协调路径合并并 CAS 保存。队列容量不会成为新的尝试额度、模型选择
授权或 JEV 次数上限。停止和 SIGTERM 仍等待实际已派发子进程清理。

## 4. DSH 初始化与验证重叠

预热必须执行真实的运行时准备，不能把普通 thread ID 续用改名为预热。本轮使用
DSH SDK 的公开 initialize 能力；只准备运行时，不先派发 Review prompt、不让
模型预测验收结果，也不启动标题或压缩等额外模型调用。其他 harness 保持已有冷
启动，不虚构 Codex、Claude 或 Kimi 的公共 warm API。

串行 packet 的 Execute 确认完成后，可为下一次 Review 初始化一个 runtime，
同时运行确定性验证。Review 真正调用仍需先满足所有适用检查、独立角色、绑定、
权限、预算与候选身份要求。Quick 与 Full 的阶段语义保持，预热不减少检查集合。

并行 Execute／L1 lane 不准备或持有预热实例；独立并行组全部停稳后，其串行
Review 路径才可开始准备。该路径的并行 L1 已经结束，不能把各 lane 的 L1 时间
都记作隐藏的初始化等待。主要重叠机会是串行 Execute 后的 L1 与适用 Quick
检查。共享候选批次、仅执行 Execute 的单阶段操作和明确暂停在 Review 前的
流程不预热。

每次至多一个待用 runtime，不跨任务或角色共享。消费时重核实际后端、模型、
账号渠道、目录、权限及必要会话参数；不匹配则关闭该实例。验证失败、流程升级、
暂停、预算阻止或取消时，未使用实例也必须等待有界 shutdown。关闭具有独立的短
宽限期，之后由 watchdog 取消并等待进程组清理，不能一直等待原模型的 wall
预算。未知清理不能用“预热可选”解释成成功。

待用实例的准备准入上限为 60 秒，到期立即禁止正式移交，再给正常关闭最多三秒
宽限，超过后强制收束。只有尚未尝试正式 start、原私有回执明确证明未派发、
SDK 与进程组已清理、输出可信且当前调用未取消或超时，安全过期才可回退一次冷
启动。冷调用沿用同一已持久化 invocation／RequestID，只消费原调用剩余 wall／
idle 时限，不增加业务尝试或预算；正式派发可能已经发生时不做这个回退。初始化
失败本身不构成允许冷启动的证据。

这项流水化重叠的是 SDK 准备与验证。Review 推理、Plan 变更和 Git 交付继续遵守
现有安全屏障；无需为追求流水程度将它们与仍在写入候选的 worker 并发。

### 持久清理责任

准备前 Go 保存单个 `state.worker-prewarm`，记录 ID、role／scope、绑定摘要、
开始时间与 run。私有 `.control/prewarm/` 保存原终态回执。重启只核对原记录，
不续用 worker；回执身份精确匹配、明确没有发送 prompt、SDK 已确认清理、记录的
worker 与其原进程组均已退出时，才解除责任。发布回执须同步文件与所在目录；
恢复时重新确认两项持久化。实际没有启动进程的分支只能用本地明确记录的
no-process 回执证明，不能凭缺失 PID 或等待时间推断。任一事实缺失仍阻断，
关闭优化同样不能跳过。

首次准备将 `state.sessions.version` 提升为 3，后续操作不得降回 2；新引擎兼容
1／2／3，旧引擎因不认识 3 而拒绝任务。版本标记防止旧版忽略新的清理责任，
不改变 `sessions.policy-version:1` 或各 worker／lifecycle 的协议版本。业务模型
调用仍具有自己的意图、预算和终态记录，准备回执不能替代它们。

## 5. 已有候选接纳评估

当前有受管 Session `claim → return` 路径：先要求已有 packet Session 的原调用
已消费并确认清理，核对绑定与历史后接管；交回运行 L1、适用 Quick gate 与独立
Review，保存候选绑定的 `source:human-takeover`，后续由正常引擎交付。

这条路径不接受一个从未具有受管 Session 的任意预先修改，也不通过 Verify／Review
两次单步自动补造 Executor 来源。原整体方案把通用候选接纳明确列为可独立排期，
因此本轮完成评估并保留真实能力边界，不扩展为自动 patch 导入。

未来通用入口须用 revision-bound 请求明确 packet、原基线、实际执行目录、真实
来源和完整候选身份；检查保护验收与实现边界，拒绝绕过未知调用。外部来源证据可
替代不存在的模型执行记录，不能编造 done-report。完整验收、独立 Review、合成候选
复验与 Git 持久化仍使用同一交付链。

## 6. 工程验证矩阵

| 场景 | 必须证明的行为 |
| --- | --- |
| 旧配置、默认模板、显式开关 | 旧 serial 与 batch 保持；新字段合法加载、保存、读回；JEV 不被调度编辑开启 |
| 长短不一的独立 packet | 前一个 Execute／L1 槽位释放即补位，总并发不超限 |
| 依赖、写入冲突、缺少声明 | 不因 ready queue 提前派发或改变串行资格 |
| 首窗／后续目录准备失败 | 保存成功前不派发；后续停止接纳并收束；未派发项无虚构状态 |
| 尝试耗尽、空转、JEV、重规划 | 原失败和决策预算保持，停稳再规划，修订后重新选择 |
| hard 预算与渠道限制 | 实际调用遵守原限制，消费持久化后才释放必要额度 |
| 共享 checkout 与集成 | 共同候选屏障保持，集成后复验，失败保留成果 |
| 真实初始化但尚未派发 | 模型 prompt 数量为零；串行准备与验证可观察地重叠；并行 lane 不积累实例 |
| 正常消费／未使用／身份变化 | 只消费匹配实例，未知或清理未确认阻止继续 |
| 安全过期／准备失败 | 只有精确未派发、清理与时限证明允许同一 invocation 冷启动一次；不重置额度 |
| 超时、取消、进程退出 | Close 有独立关闭宽限；等待所有拥有的子进程清理，SIGTERM 和原回执恢复保持 |
| 预热中断后重启、关闭开关 | 原无 prompt 清理回执、文件／目录同步和整个进程组退出均确认才解除；缺失／错配保持阻断，存储版本不降级 |

Go 执行仓库逐函数 100% statement coverage 门禁及针对并发路径的 race 检查；
worker／插件执行行为与跨进程桥接检查。离线 fixtures 使用真实受管子进程和公开
适配器路径，记录支持后端与跳过项，不能用 mock 名称冒充实际能力。必要的文档、
schema、打包入口和双语界面检查与实现一起完成。

## 7. 后续真实验收

用固定初始快照、相同契约／oracle、模型绑定、账号渠道、并发与预算比较 batch／
ready queue、冷启动／预热。包含不同 packet 耗时、验证短于／长于初始化、经常
返修、共享目录与取消恢复等任务，分别报告冷／热条件和资源利用，不把并行区间
简单相加。

首要门槛仍是可信交付与恢复正确。随后比较端到端达到验收的时间、尾延迟、失败
任务消耗、初始化与验证重叠、预热实际消费率及闲置资源。没有计量的 token／cost
保留 unknown；准备完成不证明模型质量或总时延改善。真实收益成立后再决定安装
默认策略，任何默认迁移和真实用户配置更新均单独处理。
